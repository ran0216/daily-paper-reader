# TPCS: A Cycle-Level Simulation Paradigm with Native Execution Semantics for RTL Modeling and Generation 

Chengzhen Meng ∗, Xiaoyu Li †, Chen Bai ‡, Zhenyu Zhang †, Hongjun Dai ∗∗ School of Software, Shandong University, Jinan, China † School of Integrated Circuits, Shandong University, Jinan, China ‡ Fudan University, Shanghai, China 

Abstract —The growing diversity of domain-specific architec-tures and microarchitectural designs demands fast and accurate evaluation methods during early design stages. However, existing approaches suffer from a fundamental trade-off: high-level simu-lators offer speed but lack fidelity, while RTL-based tools provide accuracy at the cost of significant simulation overhead. This gap limits efficient pre-RTL microarchitecture exploration. Therefore, we propose Transaction-Pruned Cycle Simulation (TPCS), anovel modeling and simulation framework. It serves as a unified intermediate abstraction spanning microarchitecture modeling, cycle-accurate simulation, and synthesizable RTL implementa-tion. TPCS organizes combinational logic as transaction-based function invocations and leverages host CPU control flow to naturally prune inactive logic, eliminating the need for explicit event scheduling or signal tracking. This enables cycle-accurate simulation with significantly improved performance. TPCS pre-serves structural correspondence with RTL and supports auto-matic generation of synthesizable designs. TPCS achieves 36 ×-42 × speedups over parallel Verilator on SMP systems and 3.4 ×-7.2 × over single-threaded Verilator on accelerators, with cycle-level waveform agreement on the evaluated traces. The generated RTL demonstrates comparable timing and area to handcrafted implementations, with relative changes of -4.7% to +2.6% in clock period and -3.3% to +4.0% in standard-cell area. By bridging the abstraction gap between high-level modeling and RTL design, TPCS enables a unified and agile pre-RTL workflow, allowing efficient microarchitecture exploration with both high performance and implementation fidelity. 

Index Terms —Microarchitecture Modeling, Cycle-Accurate Simulation, Hardware/Software Co-Design, Design Methodology.

However, existing simulation or evaluation tools fall into two opposing abstraction levels (Fig. 1(a)). This polarization stems from a fundamental mismatch in design philosophies: high-level tools (e.g., GEM5, TLM) prioritize exploration agility over detailed hardware behavior, while RTL tools and hardware description languages (HDLs) prioritize low-level fidelity but incur substantial simulation overhead. Consequently, the resulting design misalignment, time overhead, and engineering effort form key bottlenecks in agile μarch iteration. Addressing these challenges is fundamentally difficult, as they originate from the absence of an execution model bridging high-level programmability and low-level hardware behavior. This motivates a rethinking of how hardware execution is represented and simulated. The overhead of RTL simulation largely stems from signal-level evaluation, where even inactive computations incur un-necessary work. signal-level abstraction. We observe that hardware behavior is inherently governed by control logic, which determines the activation of entire computation blocks. Based on this, we reformulate hardware simulation as an execution process based on behavioral descriptions. Inactive paths are naturally skipped via host-native control flow, eliminating the need for explicit activity tracking. This formulation not only improves simula-tion efficiency, but also provides an executable representation of hardware behavior prior to RTL realization. In this paper, we propose Transaction-Pruned Cycle Simu-lation (TPCS), a novel methodology for modeling and simu-lating deterministic cycle-synchronous hardware designs using native software descriptions. TPCS represents hardware exe-cution as transaction-level function invocations within each cycle, enabling control-flow-driven execution with implicit pruning of inactive logic. This design achieves three key properties (Fig. 1(b)): (1) cycle-level equivalence with RTL at module boundaries, (2) high simulation efficiency through na-tive execution, and (3) structural correspondence that supports automatic generation of synthesizable RTL. Together, these properties enable fast and accurate pre-RTL design evaluation for agile hardware development. We evaluate TPCS across designs with varying control intensity. TPCS achieves 36 ×–42 × speedups on SMP systems and 3.4 ×–7.2 × on accelerators against parallel and single-threaded Verilator baselines, respectively. Meanwhile, wave-form equivalence is preserved for key registers and module boundaries. These results demonstrate that TPCS de-livers both high simulation performance and implementation-quality hardware. The main contributions of this paper are as follows:

III. T RANSACTION -P RUNED CYCLE SIMULATION 

A. Overview of TPCS 

To bridge high-level modeling and RTL fidelity, we propose Transaction-Pruned Cycle Simulation (TPCS), a modeling and simulation paradigm with native execution semantics. The term “Transaction-Pruned” refers to the elimination of inactive code execution in each cycle via transaction-based control-flow conditions, thereby pruning unnecessary simulation work. TPCS comprises three aspects: (1) modeling abstraction (Section III-B), (2) execution semantics (Section III-C), and (3) RTL generation (Section III-D). Fig. 2 illustrates the TPCS workflow using a producer-consumer example, which will be referenced throughout this section. TPCS differs from traditional HDLs by focusing on behav-ior rather than construction (Fig. 2(a)). The key challenge is to give a precise and executable definition of behavior . To this end, TPCS defines each hardware module in three aspects: (1) A set of states representing cycle-boundary observable values, with non-blocking assignment effective at next cycle (pink-shaded texts). (2) Transactions capturing inter-module control and data interactions via request (caller) and service (callee), with transaction readiness condition (blue-shaded texts). (3) Behavioral procedures expressed as C++ code operating on states and transactions within a cycle. Together, these define the complete per-cycle semantics of a module as deterministic state transitions and interactions under given inputs. This unified abstraction forms a precise and executable pre-RTL representation that is both human-readable and structurally aligned with RTL. At the software level, TPCS models are directly executable: advancing one cycle corresponds to executing per-cycle be-haviors of all modules (Fig. 2(b)). The key challenge is to achieve high performance while preserving cycle accuracy. TPCS addresses this by statically resolving control flow. State assignments are mapped to C++ APIs, and transaction interac-tions are mapped to function calls. Therefore, the execution of a cycle is driven entirely by host-language semantics without global schedulers or event queues. Transaction conditions and control-flow branches naturally prune inactive code at runtime, incurring only minimal branch prediction cost and no additional activity tracking. As a result, TPCS achieves near high-level simulation performance while maintaining cycle-level fidelity. At the hardware level, the structured abstraction of TPCS enables systematic generation of synthesizable RTL (Fig. 2(c)). The key challenge is to translate behavior and trans-action into signal-level implementations while preserving se-mantics. TPCS adopts a structure-logic decoupled approach. Module hierarchy, state, and transactions are directly mapped to an RTL skeleton with modules, registers, and port con-nections. Behavioral procedures are translated into equivalent combinational logic via the dedicated TPCS compiler. This separation establishes a consistent mapping from high-level behavior to signal-level implementation, ensuring equivalence in state transitions and interactions between the TPCS model and generated RTL.

1) Module-Centric Abstraction: TPCS adopts a module-centric abstraction, representing hardware as a hierarchy of modules. Each module structurally corresponds to an RTL module or a C++ template class. An instance denotes aconcrete instantiation of a module within its parent module. Modules are parameterized, with parameters treated as local constants specified at instantiation. This design ensures struc-tural correspondence with both RTL and C++, enabling direct execution and systematic translation. State elements capture both stored and intermediate values and are categorized into two types. Persistent state represents cross-cycle values (analogous to registers) and is updated via deferred assignment, taking effect in the next cycle; it may have multiple assignment ports with different priority. 

Ephemeral state represents intra-cycle temporary values (anal-ogous to wires), which are cleared each cycle and used for sharing intermediate results across logic blocks. For a persistent state r, let rt be its value in cycle t, and let Wt = {(p, d p)} denote all writes issued in that cycle with r.set<p>(d_p) , where p denotes the port priority, dp

denotes the data. Reads always observe rt. If Wt̸ = ∅, the state transition is rt+1 = dp∗ , where p∗ = max {p | (p, d p) ∈ Wt}.Otherwise, rt+1 = rt. Hence, writes are deferred to the next cycle and conflicts are resolved deterministically by priority, corresponding to synchronous RTL non-blocking assignment with priority arbitration. 

2) Transaction System: The transaction system is the cen-tral abstraction in TPCS. A transaction represents a single-cycle control and data interaction between modules. Trans-actions may be handshaked , where invocation takes effect only when the callee is ready, whereas a non-handshaked transaction is always accepted once invoked. Modules expose transaction ports that define invocable interactions. A request port initiates a transaction, while a ser-vice port responds. Each port optionally specifies exchanged data, including arguments from the request side and responses 

from the service side. An invocation implicitly encodes a valid 

signal, while the return value (for handshaked transactions) represents ready .Ports can be connected when their return types, arguments ,and responses match. Connections are directional: invoking the source port forwards this call to its destination, decoupling port declaration from execution while preserving RTL-style binding semantics. Connections must have neither multiple drivers nor dangling ports. Specifically, a child’s request port must be connected to a child’s service , a parent’s request , or bound to logic block(s); a parent’s service port must connect to a child’s service 

or be bound to logic block(s). Broadcast is allowed only for transactions without handshake or responses ; otherwise, connections are one-to-one. 

3) Logic Blocks: Combinational logic in TPCS is expressed as logic blocks , implemented as C++ functions. A logic block defines intra-module behavior, including state access, control flow, and transaction invocation. Logic blocks execute only when bound to triggering points, including service , triggered by transaction invocation, and tick , invoked once per cycle. This programmatic form is precise, deterministic, and exe-cutable, enabling pre-RTL validation at both module-level and system-level. TPCS imposes three constraints to define unambiguous model semantics for subsequent software execution and hard-ware generation. First, each block must terminate and produce deterministic results for all valid inputs, with fully defined control paths, statically bounded loops, statically allocated storage, and no undefined operations. Second, conflicting state updates require explicit resolution rules: order-independent blocks use priority-based deferred assignments, whereas ex-plicitly ordered blocks allow later updates to override earlier ones (as shown in Fig. 2(a)). Finally, each transaction may be invoked at most once per cycle, where a state assignment port is also treated as a special transaction. The single-invocation constraint is enforced at three stages. C. TPCS Native Execution Semantics 

This section describes the execution of TPCS models as native C++ programs. This section describes transaction invo-cation, execute-commit simulation, and deterministic parallel execution. Static execution ordering that allows native control-flow execution without runtime dependency resolution. Transaction connections are realized via C++ function calls, eliminating scheduling and activity detection. The evaluation order of logic blocks is fixed at construction time, removing runtime dependency resolution. Due to avoiding global structures such as event queues, TPCS eliminates unnecessary ordering con-straints and enables efficient cycle-level parallel simulation. 

1) Transaction Calls and Connections: Transaction con-nections underpin TPCS execution semantics. As shown in Fig. 5, transactions are implemented as C++ function calls via function-pointer-based binding. Both request and service ports are member functions. The request invoked by logic blocks forwards this call through a function pointer, while service 

acts as the entry point. Connection is realized by a generated static wrapper function whose pointer is bound to the request side. The wrapper function dispatches this call to connected child instance service or bound logic blocks. These codes are automatically derived from the structural specification, requiring only port and connection declarations. Without devirtualization, each connection incurs an indirect call that limits inlining. When a module type is instantiated under different parents, a shared call site may target different wrappers; optional wrapper duplication trades code size for execution efficiency. For arrayed child instances, frequent wrapper invocation increases overhead. TPCS mitigates this with an optional aggregation optimization that inlines the child module into parent module, enabling direct calls across siblings. This preserves functional equivalence while trading code size for speedup, and is particularly effective for regular arrays of small processing elements. 6

2) Dual-Stage Cycle-Driven Simulation: Each simulation cycle consists of an execute stage and a commit stage. During the execute stage, the tick port of each module is invoked, and logic blocks recursively trigger additional request ports as needed to evaluate dependent combinational logic. The result-ing call structure follows the host’s native control flow and directly captures hardware control semantics. In the commit 

stage, all deferred assignments are applied and prepared for the next cycle. Execution naturally follows an ordered traversal of the mod-ule hierarchy. Each module provides an exec entry function, which invokes its own tick and all children’s exec in the order constructed from logic block priorities. The exec function of the top instance is the entry point of the execute stage. In contrast, the commit stage is order-independent, as state elements are updated individually. Variables follow the convention that i denotes an instance, p a parent or ancestor, and c an immediate child. Here, H denotes the instance hierarchy, D[i] contains the precedence pairs of logic blocks within i, and S[i] is the resulting local execution sequence in i. The algorithm assumes resolved, nonrecur-sive calls without repeated block invocation, and dependency pairs whose endpoints both have owners. Unresolved calls, conflicting ownership, or cyclic ordering constraints cause a design fatal. Logic blocks without specified priority impose no additional ordering. 3) Parallel Execution: TPCS adopts static parallelization at component boundaries (Fig. 6). Only order-free instances may be assigned to different worker threads, and the partition is fixed before simulation and remains unchanged during exe-cution. All persistent and ephemeral states of an instance are exclusively owned and written by its assigned thread. Cross-thread interactions are restricted to pipe or side-effect-free ser-vices that only read persistent states; ordinary service/request interactions with cross-thread side effects are disallowed. Cross-thread pipe communication follows the execute– commit semantics. During execute , the producer and con-sumer independently update thread-local enqueue and dequeue buffers, while persistent pipe state remains unchanged. After an acquire/release spin barrier, the enqueue-side owner de-terministically commits both endpoints to the canonical pipe state. A second barrier separates commit from the next execute stage, so transferred data becomes visible only in the following cycle. Therefore, worker interleaving cannot introduce data races or affect cycle-boundary state: each thread writes only private state during execution, while all cross-thread effects are applied at deterministic synchronization points. The per-thread execution order and instance-to-thread map-ping are fully static, with no work stealing, randomized scheduling, or runtime arbitration; hence no simulator-side random mechanism is required for determinism. Thread pin-ning is used only to reduce performance variance and is not required for correctness. The half-cycle barriers introduce syn-chronization overhead, so parallel execution is most effective for sufficiently large designs and fewer cross-thread pipes.

IV. E XPERIMENT AND VALIDATION 

We evaluate TPCS through four complementary experi-ments:  

> •

Cross-abstraction correctness (Section IV-B) : Compare waveforms and workload results between direct execu-tion and generated RTL to verify that simulation gains preserve the evaluated cycle behavior.  

> •

System-level performance (Section IV-C) : Measure SMP simulation speed, parallel scalability, and overheads to assess efficiency on large-scale practical systems.  

> •

Direct HDL comparison (Section IV-D) : Hold microar-chitecture constant to compare simulation speed and RTL quality across existing HDL workflows, and use ablation to assess dedicated compiler optimization.  

> •

Hardware applicability (Section IV-E) : Evaluate AES and systolic-array designs under different input activity and transaction granularity to test effectiveness beyond CPU pipelines. 

A. Experiment Setup 1) Platforms and Toolchain: All experiments are conducted on a PC equipped with a Intel i9-14900K processor and 128 GB of DDR5 memory, running Ubuntu 22.04. Verilator 5.036 is used as the baseline in all experiments. Both TPCS code and Verilator-based simulation code are compiled using g++ 11.4 with the C++20 standard and -O3 optimization. The TPCS RTL generation scripts are executed on Python 3.11, with LLVM/clang 18.0 as TPCS compiler front-end. 9

2) Target Hardware Design: Fig. 9 illustrates the μarch de-tails of the three target hardware designs. The scalable RISC-V SMP system adopts a standard 5-stage in-order pipeline, similar to Rocket [31], with BTB, BHT, RAS predictors and a 32KB 4-way L1 cache. A lightweight atomic cache system is used as the memory subsystem. The ASIC targets, including an AES encryption unit and a systolic array, follow conventional dataflow architectures. The AES unit is implemented with one or two pipeline stages (denoted as AES1 and AES2 ), while the systolic array is instantiated in two sizes, 8x8 and 16x16 (denoted as SA8 and SA16 ). The RISC-V SMP system executes workloads pre-loaded into memory, while the accelerator designs are driven by a test harness providing streaming inputs and collecting outputs. The harness is shared between TPCS and Verilator, differing only at the transaction or signal interface. For the SMP and accelerator simulation experiments, TPCS execution is compared with Verilator simulation of RTL generated from the same model. Handcrafted SystemVerilog implementations provide references for RTL quality evalu-ation, preserving the same module hierarchy and register definitions. Section IV-D additionally compares handcrafted SV and Chisel, SystemC, PyMTL, and TPCS implementations of the same CPU pipeline in both simulation performance and RTL quality. 

3) Workloads: For the RISC-V SMP system, CoreMark 

and RISC-V bmarks bare-metal benchmarks are used. A custom checkpoint instruction signals workload start and end, implemented as a dedicated pull-up signal (or transaction) connected to the top-level module. This mechanism is used only for timing measurement. For the accelerator targets, two input patterns are evaluated. In the Full mode, data is continuously supplied to fully utilize the pipeline. In the Burst mode, input is periodically stalled to emulate intermittent availability: after every 10 input batches, the stream pauses for an equal duration. For example, pauses last 100 cycles for AES (10 cycles per batch) and 80 cycles for an 8x8 SA (8 cycles per matrix). Identical input patterns are applied across all implementations. 

4) Simulation Configuration: For correctness validation, waveform-level comparisons are performed. In the RISC-V core, valid signals and PCs of each pipeline stage are traced, while for accelerators, top-level I/O ports are monitored. Simulation speed is measured in simulated cycles per sec-ond, with waveform dumping disabled during performance measurements. The SMP experiments measure benchmark execution phases using checkpoint timing; the direct pipeline comparison follows the fixed-workload protocol in Section IV-D, and accelerator measurements use continuous 10-minute execution windows. Each comparison uses identical work-loads, inputs, and initial states across implementations. For multithreaded RISC-V SMP simulation, Verilator uses its default parallel strategy, while TPCS evenly distributes cores across threads. The simplified memory controller is assigned to the first TPCS worker thread. All threads are pinned to physical cores to reduce scheduling overhead.

TPCS reaches 11.37 MCycles/s, outperforming handcrafted SV under Verilator, Chisel under GSIM, and native SystemC by 4.77 ×, 2.70 ×, and 14 .73 ×,respectively. As reference, generated RTL achieves 2.027– 2.329 MCycles/s under the same Verilator version. The isolated pipeline simulates faster but shows a smaller relative speedup than the SMP system. Removing caches and multicore interactions reduces simulation work, while single-cycle memory accesses increase pipeline utilization and limit pruning opportunities. Conversely, SMP introduces more conditionally inactive logic that TPCS can skip, while addi-tional signal-level dependencies increase Verilator’s evaluation costs. This is consistent with TPCS benefiting from inactive computation, although the reported speedups also use different RTL baselines and thread configurations. 

2) On Generated RTL Quality: TPCS achieves the shortest clock periods for the full pipeline and MDU, improving on handcrafted SV by 3.09% and 4.74%, with area changes of −3.31% and +1 .68% , respectively. FPU timing and area overheads are 2.58% and 3.77%, although PyMTL achieves a smaller area. The relatively modest timing differences on the full pipeline and MDU are consistent with differences in low-ering: the evaluated PyMTL and SystemC flows retain more readable control structures in RTL, whereas TPCS and Chisel apply more aggressive lowering and optimization through CIRCT. Relative to Chisel, TPCS has shorter clock periods but slightly larger MDU and FPU areas, consistent with an area-timing tradeoff. Across targets, similar MDU critical paths limit variation, whereas the FPU’s multiple complex arithmetic paths amplify differences in generated logic. These results show competitive RTL quality, with differences reflecting the generated logic structures. V. D ISCUSSION AND LIMITATIONS 

The experiments show that TPCS combines cycle-level agreement on the evaluated workloads with faster direct ex-ecution and competitive RTL quality. Simulation gains de-pend on input activity, transaction granularity, and parallel synchronization costs, while compiler ablation demonstrates the importance of predicate sinking for timing quality. These results support fast pre-RTL exploration using an executable model structurally aligned with its implementation. Explicit register boundaries and cycle semantics help relate backend results to modeling decisions, potentially reducing manual reimplementation and enabling earlier diagnosis of microar-chitectural bottlenecks. TPCS nevertheless has three limitations. First, usability depends on infrastructure that is not yet mature, since large-scale development requires stronger modeling diagnostics, debugging support, and reusable libraries. The native C++ representation also offers opportunities for AI-driven devel-opment, but reliable use requires dedicated validation and debugging infrastructure in the future. Second, hardware coverage remains to be extended be-yond the evaluated cycle-synchronous designs. The current TPCS semantics provide a sufficient foundation for syn-chronous composition, but broader applicability requires stan-dardized clock-domain-crossing (CDC) components, explicitly defined asynchronous primitives, and gated clocks. Although faithfully capturing physical metastability at this abstraction level is impractical, configurable-delay models may sup-port asynchronous-synchronous behavioral equivalence anal-ysis under explicit timing assumptions. Third, the compiler currently emphasizes combinational timing optimization, with limited support for automatic pipelining and systematic area-timing exploration. A future pipelining extension could let users specify the latency from block activation to output transactions, reducing practical development efforts. Closer integration with gate-level and physical-design optimization could further improve RTL qual-ity. VI. C ONCLUSION 

This paper presents Transaction-Pruned Cycle Simulation (TPCS), a modeling and simulation methodology for cycle-synchronous hardware. TPCS maps hardware control flow onto native C++ execution to prune inactive computation without explicit event scheduling, while a dedicated compiler gener-ates structurally corresponding RTL. Experiments show up to 42 × speedup over parallel Verilator on SMP systems, 4.77 ×

over handcrafted SV simulation on an isolated CPU pipeline, and 3.4 ×–7.2 × on accelerators. The evaluated designs retain cycle-level waveform agreement and achieve RTL timing and area comparable to handcrafted implementations. These results support a unified representation for fast pre-RTL exploration, validation, and hardware implementation. Future work will improve tooling and AI-assisted infras-tructure, broaden hardware coverage through standardized CDC components and asynchronous primitives, and extend the compiler with latency-aware automatic pipelining, gate-level optimization, and systematic area–timing exploration.
