# PipeDRAM : A Data-Transposition-Free In-DRAM Architecture with Hardware/Software Pipelining

Processing-using-DRAM (PUD) architectures exploit the ana-log operational properties of DRAM to perform bulk bitwise Boolean and arithmetic operations inside memory arrays by or-ganizing data in a vertical layout, where operand bits are stacked along DRAM columns. However, modern computing systems na-tively employ a horizontal data layout that preserves the cache line abstraction, leverages spatial locality in row buffers, and enables high memory throughput. This fundamental mismatch forces existing PUD architectures to frequently perform data lay-out transformations between horizontal and vertical formats, in-curring significant performance, energy, and system integration overheads. Our goal is to eliminate data transposition overheads in PUD systems at low cost. To this end, we propose PipeDRAM, a PUD architecture that eliminates the need for runtime data layout transformation, enabling PUD operations directly over horizontally laid-out data. PipeDRAM ’s key ideas are to (i) deter-ministically reorganize bits inside each memory request to enable a PUD-friendly data placement within a DRAM array in a hori-zontal data layout, and (ii) employ a pipeline-based execution model that overlaps bit-dependent and bit-independent in-DRAM operations to exploit bit-level parallelism across the memory ar-ray. We compare PipeDRAM to different computing platforms. PipeDRAM provides (i) 11.8 ×, 11.8 ×, and 80.4 × higher perfor-mance and (ii) 25.4 ×, 3.0 ×, and 38.0 × lower energy consumption than three state-of-the-art PUD systems. PipeDRAM incurs low area cost on top of a DRAM chip (1.86%) and CPU die (0.05%). To enable further research on PUD systems, we open-source PipeDRAM at https://github.com/CMU-SAFARI/PipeDRAM .

## 1. Introduction 

Processing-in-memory (PIM) [1–15] is a paradigm that allevi-ates the ever-growing cost of moving data between computing (e.g., CPU, GPU) and memory (e.g., DRAM) elements. In PIM ar-chitectures, computation is done by adding logic near memory arrays, i.e., processing-near-memory (PNM) [9, 10, 16–48, 48– 183], or by using the analog properties of the memory arrays, i.e., processing-using-memory (PUM) [15,69,109,134,184–295]). Many prior works [15, 69, 185–191, 194, 198–201, 203, 204, 210, 213–217, 220, 225, 233–237, 239, 260, 261, 266, 290–295] demon-strate the feasibility of processing-using-DRAM (PUD), which uses DRAM cells to implement ( i) simple PUD primitives , such as in-DRAM row copy [188, 194, 200, 214, 237] and Boolean/ma-jority [185–187, 191, 201, 202, 236] logic, and ( ii ) complex PUD operations , such as arithmetic [190, 216, 217, 225, 234, 235, 292] and lookup table (LUT)-based [203, 204, 233, 258, 295–297] op-erations, implemented by composing PUD primitives. PUD architectures commonly employ a bit-serial single-instruction multiple-data (SIMD) execution model to implement arithmetic and logic operations inside DRAM arrays. To enable efficient carry propagation and bitwise computation, such architectures organize data in a vertical layout: for an input array with M

data elements, each of which with N bits, this layout spans M

columns and N rows, where each DRAM row corresponds to a single bit-position of all M data elements. Multiple inputs arrays are placed in different DRAM rows and aligned within the same DRAM column. The vertical data layout mitigates two key issues that arise when performing arithmetic PUD operations under the con-ventional horizontal data organization that modern computing systems natively employ to enable high memory throughput. First, conventional DRAM interleaving schemes distribute the bits of an N -bit data word evenly across the DRAM hierar-chy [298–302] (i.e., rank → chip → bank → subarray → mat), scattering the operand bits that must interact during in-DRAM execution. Since PUD computation is driven by the sense am-plifiers of a DRAM mat [15, 185, 188, 194, 200, 201, 236, 237, 303] (the basic building block of PUD computation), this distribu-tion creates a data locality problem, where the bits of a given PUD operand are spread across the DRAM hierarchy rather than being centralized within a single DRAM mat. The vertical layout resolves this by confining all N bits of each data word to a single DRAM column, thereby localizing the full operand within one mat. Second, PUD computation is inherently row-wise , where sense amplifiers operate across all columns of an activated DRAM row, and no native interconnect exists to prop-agate data column-wise across rows [225]. As a result, PUD operations that require intermediate values to propagate across bit-positions (e.g., carry propagation in a bit-serial adder) can-not be performed under a horizontal data layout without costly hardware modifications to the DRAM array [225, 235], where the N bits of an operand reside in N different columns. Second, data layout transformation amplifies data movement and interferes with the cache hierarchy . For example, prior works [225, 235, 292] store vertically laid-out data as object slices spanning multiple cache lines, such that accessing or evicting a single data element triggers writeback of an entire slice. This amplifies cache line traffic, increases writeback pres-sure, and entangles PUD execution with CPU cache hierarchy behavior. Third, vertical-layout PUD architectures introduce a 

dual data-layout view of memory , where an application needs to distinguish between horizontally and vertically organized objects and coordinate data layout transformations. Our goal in this work is to eliminate the need for runtime data layout transformation while preserving PUD execution compatibility with conventional horizontally-organized mem-ory systems. To this end, we propose PipeDRAM , a PUD archi-tecture that enables bit-serial PUD execution directly over hor-izontally laid-out data. The key ideas of PipeDRAM are twofold. First, PipeDRAM leverages a mat-aware bit mapping (MABM) mechanism that deterministically reorganizes bits within each cache line to enable a horizontal, yet PUD-friendly, data layout within DRAM without incurring data transposition overheads. Placed at the memory controller, MABM applies a determin-istic bit-level permutation to each cache line on writes (and its inverse on reads), such that ( i) each data word is confined within a single DRAM chip, and ( ii ) its N bits are horizon-tally distributed evenly across the mats of that chip, with each mat holding one bit-position within a single DRAM row. This directly addresses the data locality problem by keeping the operand data inside a single subarray (multiple mats). MABM introduces no memory throughput loss or data format con-version overhead. Second, PipeDRAM combines fine-grained DRAM row access [304–312] with a hardware/software pipeline 

to exploit bit-level parallelism [292] in PUD execution. Since MABM assigns each bit-position to a dedicated DRAM mat, carry values must propagate mat-to-mat rather than row-to-row. PipeDRAM enables this via the inter-mat interconnect of MIMDRAM [235], a fine-grained PUD architecture that al-lows individual DRAM mats to be activated independently and provides low-cost data movement across mats. The ability to individually activate mats and move data be-tween them opens a new opportunity: to turn each DRAM mat into a pipeline stage , where each stage processes a dis-tinct bit-position of the same PUD operation. Such pipelin-ing is possible because the PUD primitives of a PUD opera-tion naturally partition into bit-dependent primitives (those on the carry-dependency chain) and bit-independent primitives (those that can execute before or after dependency resolu-tion). Hence, while bit-dependent PUD primitives advance in dependency order with carry values flowing mat-to-mat, bit-independent PUD primitives from successive bit-positions can overlap across stages, keeping multiple mats busy simultane-ously. To orchestrate this pipeline without costly runtime hard-ware, PipeDRAM statically assigns PUD primitives to pipeline stages using a classical modulo scheduling algorithm [313–315], which computes a fixed, repeating schedule offline. To keep the pipeline busy, PipeDRAM introduces a hierarchical in-DRAM data copy scheme that prevents latency-critical carry propa-gation from stalling pipeline stages. Beyond performance, 

PipeDRAM eliminates the dual data-layout view of memory entirely by operating natively over horizontally laid-out data. Since data does not need to be reorganized into a vertical for-mat, applications require no explicit data-format management, and no coordination of layout transformations, addressing the the dual data-layout view of memory limitation we described. We compare the benefits of PipeDRAM to different state-of-the-art processor-centric (CPU, GPU) and memory-centric ar-chitectures (SIMDRAM [225], MIMDRAM [235], Proteus [292]). Using a single DRAM rank, PipeDRAM provides ( i) 11.8 ×,11.8 ×, and 80.4 × higher performance, ( ii ) 25.4 ×, 3.0 ×, and 38.0 × lower energy consumption than SIMDRAM, MIMDRAM, and Proteus ; and ( iii ) 356 × and 11.7 × higher energy efficiency than a CPU and GPU, respectively, on average across twelve real-world applications. PipeDRAM incurs low area cost on top of a DRAM chip (1.86%) and CPU die (0.05%). We make the following key contributions: • We propose PipeDRAM , a new PUD architecture that enables in-DRAM computation directly over horizontally laid-out data, eliminating runtime data layout transformation and removing the need for two physical data layouts. To our knowledge, PipeDRAM is the first architecture to support pipeline bit-serial PUD execution without requiring vertical data organization. • PipeDRAM deploys a new pipeline-based execution model, which decomposes PUD operations into bit-dependent and bit-independent primitives and exploits fine-grained DRAM to overlap their execution. This execution model leverages the distributed placement of operand bits across multiple DRAM mats to enable steady-state pipelined computation over horizontally laid out data. • PipeDRAM introduces two novel components. First, 

PipeDRAM ’s MABM mechanism deterministically reorga-nizes bits within each memory request to enable PUD-friendly data placement. Second, PipeDRAM ’s hierarchical in-DRAM data copy scheme decouples carry-dependent com-munication from computation, removing data communica-tion from the critical path of PUD execution. • We extensively evaluate PipeDRAM for twelve real-world applications, showing that PipeDRAM outperforms state-of-the-art PUD frameworks and processor-centric designs while incurring low area cost to the system. • We open-source PipeDRAM at https://github.com/ CMU-SAFARI/PipeDRAM .

The first command, ACTIVATE (ACT ), connects each DRAM cell in a row to its local bitline, and each cell’s transistor shares its charge with the bitline to shift the bitline voltage higher (or lower) if the cell stores a ‘1’ (‘0’). In-DRAM Row Copy. RowClone [188] enables copying a row A to a row B in the same subarray by issuing two con-secutive ACT commands to these two rows, followed by a PRE 

command. This command sequence is called AAP . LISA [223] enables the execution of in-DRAM row copy operations across DRAM rows in different subarrays of a DRAM bank by con-necting local row buffers of neighbor subarrays using isola-tion transistors, providing high-throughput inter-subarray data copy . To do so, LISA exposes a new command to the memory controller called LISA-RISC (rapid inter-subarray bulk data copying), which moves an entire DRAM row between neigh-boring DRAM subarrays with a latency of 3×tRAS +2 ×tRP +2 × tRBM .1 FIGARO [324] allows copying one column from the local row buffer of one subarray to the local row buffer of another subarray within the same bank using a new DRAM command called RELOC .

In-DRAM Bitwise Operations. Ambit [185, 201] shows that a simultaneous triple row activation (TRA) can perform in-DRAM bitwise AND/OR/MAJ operations. Upon sensing the perturbation of the three simultaneously activated rows, the sense amplifier amplifies the local bitline voltage to VDD or 0 if at least two of the capacitors of the three DRAM cells are charged or discharged, respectively. As such, a TRA results in a Boolean majority operation (MAJ). Ambit implements TRA using a custom row decoder, and introduces a new com-mand called AP that issues a TRA followed by a PRE . Since TRA operations are destructive, Ambit divides DRAM rows into three groups: ( i) the D-group, which contains regular data rows; ( ii ) the C-group, which consists of two rows ( C0 

and C1 ) with all-‘0’ and all-‘1’ values; and ( iii ) the B-group, which contains six rows designated for computation (four reg-ular rows, T0 , T1 , T2 , T3 ; and two rows, DCC0 and DCC1 , of dual-contact cells for enabling the NOT operation). ## 3. Motivation 

In this section, we discuss the three limitations imposed by requiring a vertical data layout for bit-serial PUD execution: (i) costly runtime data layout transformation, ( ii ) amplified data movement and cache interference, and ( iii ) a dual data-layout view of memory that complicates system integration. 

Costly Runtime Data Layout Transformation. Requiring a vertical data layout for bit-serial PUD execution necessitates frequent and costly runtime data layout transformation between the system’s native CPU-friendly horizontal format and the PUD-friendly vertical format. In conventional processor-centric systems, cache lines are organized horizontally across DRAM chips and columns to preserve the cache line abstrac-tion and maximize memory throughput. Each cache line ac-cess is serviced by a single sequence of DRAM commands (ACT -RD /WR -PRE ), since all bits of the cache line reside within the same DRAM row across chips. In contrast, under vertical-layout PUD execution, the bits of an N -bit data element are distributed across N different DRAM rows, with each row cor-responding to a distinct bit-position. Consequently, reading or writing a vertically organized cache line requires N separate DRAM ACT -RD /WR -PRE execution, one per row. Since DRAM row activations dominate both latency and energy consump-tion, this N -fold amplification of DRAM traffic substantially increases memory access cost and undermines the efficiency benefits of in-DRAM computation. Amplified Data Movement & Cache Interference. Vertical-layout PUD incurs amplified data movement and cache inter-ference at cache line granularity, by tightly coupling PUD exe-cution with cache hierarchy behavior. When a cache line A

belonging to a PUD memory object is evicted from the last-level cache (LLC), the data transposition unit (placed in the memory controller) intercepts the request (see [225]). Since a vertically-organized PUD memory object distributes the N

bit-positions of each data word across N DRAM rows, writing such data at high throughput requires assembling a full vertical memory slice that spans N cache lines. Only after collecting all N cache lines, the memory controller can issue N DRAM write operations, each targeting a distinct DRAM row. 

Dual Data-Layout View of Memory. PUD architectures that rely on a vertical data layout impose a dual data-layout view of memory address space , since the system must main-tain two incompatible physical organizations, i.e., the native horizontal layout for host execution and the vertical layout required for in-DRAM computation. This duality breaks the uniform memory abstraction expected by software and com-plicates system integration, as the programmer (or compiler) must explicitly distinguish between horizontally and vertically organized memory objects and determine when a data layout transformation should occur. This decision is inherently frag-ile: if a transformation occurs too late , it lies on the critical path of the PUD operation; if it occurs too early , subsequent host accesses may consume data already reorganized into the vertical format, forcing additional layout conversions. As a result, performance depends on anticipating dynamic cache residency and future access behavior. 

Goal. Our goal in this work is to eliminate the fundamental limitations imposed by vertical data layout in bit-serial PUD architectures. We aim to remove the root cause of these ineffi-ciencies by enabling high-throughput in-DRAM computation 

directly over horizontally laid-out data, thereby eliminating runtime data transposition and avoiding dual physical data lay-outs while remaining compatible with existing conventional memory systems. 54. PipeDRAM Overview 

PipeDRAM is a PUD architecture that enables bit-serial/bit-parallel execution directly over horizontally laid-out data. 

PipeDRAM is built on two key ideas. First, it deterministi-cally reorganizes bits within each cache line to construct a PUD-friendly data placement inside DRAM while preserv-ing the system-level horizontal data layout and cache line abstraction. Second, it combines fine-grained DRAM access with hardware/software pipelining to exploit bit-level paral-lelism across DRAM mats during PUD execution. PipeDRAM 

consists of three main components. First, a mat-aware bit mapping (MABM) mechanism (§4.2), implemented in the mem-ory controller, that deterministically redistributes bits within each cache line to enable mat-level data interleaving with-out requiring runtime data layout transformation. Second, a 

software-assisted pipelined execution model (§4.3) that statically schedules PUD primitives across DRAM mats and subarrays to sustain high-throughput bit-serial execution. Third, PipeDRAM 

implements a hierarchical in-DRAM data copy scheme (§4.4) that accelerates carry propagation and removes inter-bit de-pendency communication from the critical path of the pipeline.

4.2. Mat-Aware Bit Mapping (MABM) 

PipeDRAM ’s MABM mechanism eliminates the need for run-time data layout transformation by redefining how bits within a cache line are mapped to DRAM chips and mats while address-ing the data locality problem (§1) imposed by conventional DRAM interleaving. MABM simultaneously ( i) localizes each scalar value within a single DRAM chip; and ( ii ) interleaves the bit-positions of that scalar value across multiple DRAM mats using a deterministic mapping function . This data place-ment preserves the host’s horizontal data layout and cache line abstraction, while creating the bit distribution that PipeDRAM 

requires for pipelined bit-serial execution. Each mat then holds one operand bit-position for many data elements, enabling successive mats to operate as pipeline stages and allowing dependency-critical values to be propagated through the data movement substrate described in §4.4, without runtime trans-position or costly cross-bitline communication hardware. 

Implementation. Formally, let A[i]j denote bit-position j

of scalar A[i], where N is the scalar bit-width. Let Nchips 

denote the number of DRAM chips in a rank, and let Nmats 

denote the number of DRAM mats participating in PUD exe-cution within a chip. MABM defines a deterministic mapping 

Φ( A[i]j ) = ( c, m, ℓ ), where c = i mod Nchips , ℓ = ⌊i/N chips ⌋,and m = j mod Nmats . Here, c denotes the target DRAM chip, 

m denotes the target DRAM mat within that chip, and ℓ de-notes the column group index within the mat, derived from the scalar index i; higher-order bit positions are mapped to successive mat groups. 3 This mapping ensures that: ( i) all bits of scalar A[i] reside within a single DRAM chip, and ( ii ) dis-tinct bit-positions of the scalar are distributed across different DRAM mats, enabling mat-level parallel execution of PUD primitives. When retrieving a cache line from DRAM during a read operation, the MABM mechanism applies the inverse permutation Φ−1 to the returned data before injecting it into the cache subsystem. Because Φ is bijective over the bits of a single cache line, the original horizontal cache line organiza-tion is reconstructed by applying Φ−1 to each bit read from DRAM. Specifically, a bit read from physical location (c, m, ℓ )

is restored to Φ−1(c, m, ℓ ) = A[ℓ · Nchips + c]m. Equivalently, the scalar index is recovered as i = ℓ · Nchips + c, and the bit index is recovered as j = m.Fig. 6 illustrates the operation of the MABM mechanism dur-ing a cache line eviction to DRAM (a cache line retrieval, i.e., a DRAM read, is analogous). The MABM mechanism operates in three steps. In the first step, the memory controller receives an evicted cache line (e.g., 64 B ) containing 16 scalar elements 

A[i], where each scalar is 4 B (32-bit) in this example ( 1 in Fig. 6). The cache line is organized in the conventional horizon-tal data layout. In the second step, upon receiving the cache line and prior to injecting its data into the memory controller’s write queue (not shown), the MABM mechanism applies Φ

independently to each bit A[i]j ( 2 ). 4.3. Software-Assisted Pipelined PUD Execution 

4.3.1. Pipelined Execution Flow. PipeDRAM exploits the horizontal data layout produced by MABM (§4.2) to pipeline the execution of the several PUD primitives that compose a single bit-serial PUD operation across the DRAM mats within a DRAM chip. Instead of executing all PUD primitives of bit-position i before starting the execution of bit-position i +1, PipeDRAM assigns successive bit-positions to neighboring mats and overlaps their execution whenever bit-dependencies permit. In this way, the mats within a chip act as pipeline stages that process different bit-positions of the same operation, while intermediate values propagate between mats according to the inter-bit dependencies of the PUD operation. As a result, multiple bit-positions of the same PUD operation can be in flight simultaneously across a single DRAM subarray, converting mat-level parallelism into pipeline parallelism. Fig. 7 illustrates PipeDRAM ’s pipelined execution flow using the same 2-bit in-DRAM bit-serial addition shown in the DDG of Fig. 3. The figure maps the two operand bit-positions to dif-ferent DRAM mats and shows, cycle by cycle, which PUD prim-itives are issued to each mat. In this example, mat 0 executes the PUD primitives of the least-significant bit-position, while 

mat 1 executes the PUD primitives of the next bit-position once the carry dependency becomes available. 4.3.2. Software-Assisted Instruction Scheduling. 

PipeDRAM employs a software-assisted static scheduler to construct the pipelined execution schedule of a PUD operation across DRAM mats. Unlike conventional processors, PUD execution is fully deterministic: each PUD operation corresponds to a fixed sequence of PUD primitives defined by a μProgram, with no conditional branches, dynamic memory accesses, or runtime control flow. Consequently, all data-/bit-dependencies between PUD primitives are known prior to execution. This property enables PipeDRAM to compute the instruction schedule offline and provide the memory controller with a static schedule that maps each PUD primitive to a pipeline stage (i.e., DRAM mat) and execution cycle. To do so, PipeDRAM adopts a scheduling strategy inspired by iterative modulo scheduling [313], widely used in very long instruction word (VLIW) compilers [327–331] to construct static execution schedules. By assigning each path to the communication it serves best, PipeDRAM removes carry propagation from the critical path of pipelined PUD execution while preserving low hardware cost. PipeDRAM logically par-titions neighboring (i.e., physically adjacent, sharing a local row buffer) subarrays into two roles. A computing subarray 

executes PUD primitives over the active pipeline stages, while a neighboring copying subarray serves as a temporary staging area for intermediate values that must be forwarded to sub-sequent pipeline stages. This organization allows PipeDRAM 

to remove carry-dependent communication from the critical path of computation: latency-critical values are first trans-ferred quickly to a copying subarray using the inter-subarray interconnect, and are then propagated asynchronously to the appropriate destination mats using the low-cost inter-mat in-terconnect. It is important to point out that the adoption of a copying subarray during PUD execution does not reduce the effective memory capacity of the DRAM subsystem, since the copying subarray is used as a staging buffer that only occu-pies the copying subarray’s local row buffer and does not hold any state during PUD operation, i.e., user data stored in the copying DRAM subarray is preserved. In case the PUD system enables PUD execution across all DRAM subarrays in a DRAM bank, a copying subarray can be time multiplexed between copying and computing across PUD execution, since enabling a copying subarray does not involve any static resource partition-ing and requires only that PipeDRAM appropriately schedules the inter-subarray/-mat DRAM commands (discussed below) during PUD execution.

4.5. Discussion 

Execution Model. PipeDRAM converts mat-level parallelism within a chip into pipeline parallelism for a single PUD op-eration, while preserving chip-level MIMD parallelism across the logical subarray. This execution model differs from prior fine-grained PUD architectures, such as MIMDRAM [235]: while they exploit data-level parallelism across multiple PUD operations, PipeDRAM exploits bit-level parallelism within a 

single PUD operation. However, it is important to point out that PipeDRAM can also exploit data-level parallelism, since operand bits are interleaved across DRAM chips via our MABM scheme, enabling different DRAM chips within the same logi-cal DRAM subarray to execute independent PUD operations 

concurrently , and thereby support MIMD-style execution. 

Programming Model, ISA & System Support. PipeDRAM 

leverages the same ISA extensions, compiler support, control unit, and coherency mechanism as prior PUD systems [225,235, 292]. It is important to point out that our MABM mechanism (§4.2) requires no knowledge of the data type or bit-precision of the cache lines the memory controller writes/reads to/from DRAM. MABM’s deterministic mapping Φ is defined over fixed-size M -bit words ( M = 64 bits in our design) and is applied identically to every cache line, so a DRAM read returns exactly the cache line the preceding write stored, regardless of how software interprets its bytes. The bit-precision M is needed 9only during the execution of a PUD operation, and such in-formation is present in the ISA extensions we inherit from SIMDRAM [225] and MIMDRAM [235]. 

Execution Control. PipeDRAM leverages MIMDRAM’s con-trol unit [235], placed at the memory controller, to fetch, de-code, and dispatch bbop instructions to DRAM. When the memory controller receives a bbop instruction, the control unit decodes the instruction to identify the corresponding μProgram and retrieves its precomputed pipeline schedule from a dedicated pipeline schedule table . This table stores the static schedule produced by Algorithm 1 for each μProgram, mapping every PUD primitive to a (mat, cycle, stage) tuple. The control unit streams the retrieved schedule entries to the 

μProgram processing engine , which issues PUD primitives to the corresponding mats according to the precomputed order. 

## 5. Methodology 

We implement PipeDRAM using an in-house cycle-level sim-ulator (which we open-source at [333]) and compare it to prior simulated state-of-the-art PUD frameworks, i.e., ( i) SIM-DRAM [225], a coarse-grained bit-serial PUD architecture; (ii ) MIMDRAM [235], a fine-grained bit-serial PUD architec-ture; and ( iii ) Proteus [292], a coarse-grained bit-parallel PUD architecture. Our in-house simulator was rigorously validated against the gem5 [334] implementations of SIMDRAM and MIMDRAM [335] and accounts for the additional latency im-posed by SALP-MASA (multitude of activated subarrays) [316] on DRAM ACT commands, i.e., the extra circuitry required to support SALP incurs an extra latency of 0.028 ns to an 

ACT [336] (which is less than 0.11% extra latency for an AAP ). 5

## 6. Evaluation 

We demonstrate the advantages of PipeDRAM by evaluating (i) PipeDRAM ’s throughput for sixteen bit-serial and four bit-parallel PUD operations at 4- to 32-bit precision, in comparison to three state-of-the-art PUD systems, i.e., SIMDRAM [225], MIMDRAM [235], and Proteus [292] (§6.1); ( ii ) PipeDRAM ’s performance, energy consumption, and energy efficiency for twelve real-world applications, in comparison to the three PUD systems, a multicore CPU, and a high-end GPU (§6.2); (iii ) PipeDRAM ’s load balance and pipeline utilization across DRAM mats and DRAM chips (§6.3); and ( iv ) the SIMD-width 10 trade-off between PipeDRAM ’s pipelined execution and SIM-DRAM’s full-row execution for varying bit-precision and num-ber of data elements (§6.4). Finally, we evaluate two key over-heads in PipeDRAM : exposed carry-propagation latency (§6.5) and area cost on top of a DRAM chip and CPU die (§6.6).

6.3. Load Balance & Pipeline Utilization 

Fig. 12 quantifies the PipeDRAM ’s utilization of each of the 32 mats within a DRAM chip (left) and of each of the four DRAM chips (right) for our twelve real-world applications. A mat’s utilization is the fraction of time it is busy; a chip’s utilization is the average mat utilization across 32 mats. We make three observations. First, PipeDRAM achieves high uti-lization at both mat and chip granularities. Averaged across our twelve workloads, intra-chip (mat) utilization is 87% (93% across the eleven 32-bit workloads), and the four chips are utilized identically, with inter-chip imbalance below 0.04%. This happens as a consequence of our two mechanisms act-ing together: MABM distributes each operation’s bit-positions across the 32 mats, and PipeDRAM ’s modulo scheduler exe-cutes the bit-independent PUD primitives of one bit-position in its mat while the carry-dependent primitives of the neigh-boring bit-position execute in the adjacent mat, so that every mat stays busy. Chip balance is structural, since MABM places data element i on DRAM chip i mod 4 , each group of 2,048 consecutive data elements that one PUD primitive operates on has exactly 512 data elements on each of the four chips. Only the last such group of an operation whose element count is not 

a multiple of 2,048 can have more data elements on one chip than on another, by at most one data element per chip. Second, the residual intra-mat load imbalance is caused by the deployed bit-serial algorithm, not by PipeDRAM ’s pipeline structures. Each bit-serial operation has a characteristic per-bit-position work distribution: ( i) multiplication is the most uneven PUD operation, since a result at bit-position m accumulates every partial product Aj · Bk with j+k=m, so its per-bit work is maximal at the middle result bits and minimal at the least-and most-significant bits; ( ii ) division is monotonic, since its low-order quotient bits operate on a wider intermediate re-mainder, so per-bit work decreases from the low-order to the high-order quotient bits; ( iii ) addition/subtraction and the logic bitwise operations are nearly uniform. MABM reduces the mul-tiplication imbalance at no cost by assigning bit-positions j

and j+32 to the same mat, and because multiplication’s work is symmetric across its midpoint, these paired positions sum to nearly equal per-mat work across all 32 mats. We observe that the seven multiplication-dominated applications ( 2mm , 3mm ,

6.4. SIMD-Width Trade-Off Analysis 

PipeDRAM reorganizes PUD parallelism rather than reduc-ing it. As Table 1 shows, PipeDRAM ’s peak SIMD width is 

2,048 ×#bit-precision, since each bit-position of a PUD opera-tion occupies one mat (512 columns across four chips, i.e., 2,048 lanes). Therefore, two parameters set PipeDRAM ’s throughput: (i) bit-precision fixes how many mats a single PUD operation occupies, and thus its width; ( ii ) number of data elements fixes how many 2,048-element batches iterate through those mats. A single batch occupies one mat at a time, and once enough batches are in flight to fill all #bit-precision mats, PipeDRAM 

reaches its steady-state width of 2,048 ×#bit-precision (65,536 at 32 bits, matching SIMDRAM’s row granularity). Which or-ganization is faster, PipeDRAM ’s pipeline or SIMDRAM’s full row, depends on both the bit-precision and the number of data elements per PUD operation. Fig. 13 quantifies this trade-off by showing PipeDRAM -Hier’s compute-only throughput relative to SIMDRAM, with no data transposition for either system, across both parameters, for multiplication (the dominant oper-ation in seven of our twelve applications); markers show where the twelve applications fall. SIMDRAM’s bit-serial latency grows quadratically with pre-cision for multiplication, whereas PipeDRAM ’s steady-state throughput is precision-independent. Therefore, PipeDRAM -Hier has the same performance as SIMDRAM at 23 bits and is 

1.4× faster than SIMDRAM at 32 bits. 6.6. Area Analysis 

Area Analysis. We use CACTI 7.0 [332] to evaluate the area overhead of PipeDRAM using a 22 nm technology node, fol-lowing the methodology of prior PUD works [225, 235, 292]. 

DRAM Chip Area Overhead. PipeDRAM does not intro-duce any new modifications to the DRAM array circuitry. It builds on three existing DRAM enhancements: ( i) the fine-grained mat access substrate of MIMDRAM [235], including mat isolation transistors, row decoder latches, mat selectors, and the inter-mat interconnect, which incurs 1.11 % area over-head on a DRAM chip [235]; ( ii ) the inter-subarray isola-tion transistors of LISA [223], which incur 0.6 % area over-head [223,292]; and ( iii ) the SALP circuitry [316], which incurs 0.15% area overhead [292,316]. In total, PipeDRAM incurs 1.86% area overhead in a DRAM chip. 

MABM Area Overhead. The MABM mechanism (§4.2) implements the deterministic bit permutation Φ and its in-verse Φ−1 on the memory controller’s cache line data path. Because the permutation is a static rewiring of bit positions within each cache line, it is a fixed bit permutation that requires 

no logic gates: only wire routing. To confirm this, we imple-mented both Φ and Φ−1 in Verilog HDL and synthesized them using Yosys [350], an open-source synthesis framework, target-ing the open-source Nangate 45 nm standard cell library [351]. Both permutations synthesize to zero logic cells ; the mapping is implemented entirely through wire routing, incurring no logic gate area, latency, or power overhead. 

Memory Controller Area Overhead. PipeDRAM lever-ages MIMDRAM’s existing control unit [235] to fetch, decode, and dispatch bbop instructions. PipeDRAM extends this control unit with a pipeline schedule table that stores the precomputed static schedule (Algorithm 1) for each μProgram. Each schedule entry maps a PUD primitive to a (mat, cycle, stage) tuple, re-14 quiring 4 B per entry. For our 16 bit-serial operations at 32-bit precision, the largest schedule (division) contains 1,350 entries, requiring 5.3 kB . We provision a 16 kB schedule scratchpad, sufficient to hold the schedules for all evaluated operations si-multaneously. Using CACTI, we estimate the extended control unit area to be 0.27 mm 2, comparable to MIMDRAM’s control unit ( 0.253 mm 2 [235]). 

Total CPU Die Area Overhead. Considering the MABM logic (negligible area) and the extended control unit (0.27 mm 2), PipeDRAM ’s total memory controller-side area is 

0.27 mm 2. This represents 0.05% of the die area of a state-of-the-art Intel Xeon E5-2697 v3 CPU [197]. PipeDRAM ’s CPU-side area is smaller than that of SIMDRAM, MIMDRAM, and 

Proteus because it eliminates the 0.06 mm 2 transposition unit that both prior works require. We conclude that PipeDRAM incurs low area cost on top of a DRAM chip (1.86%) and CPU die (0.05%), while eliminating the data transposition unit required by all prior PUD architectures. 

Implementation Complexity & Practical Deployability. 

PipeDRAM adds no arithmetic logic to the DRAM array. The cost and complexity of such logic arise from building it in density-optimized DRAM [18, 352]. PipeDRAM ’s DRAM-side modifications are limited to structural circuitry (i.e., isolation transistors, latches, and narrow interconnects) that reuses the existing sense amplifiers as the compute substrate. These changes are modular, touching disjoint subarray structures, so their area costs simply add (1.11% + 0.6% + 0.15% = 1.86%), with no extra cost from combining them. We make two key ob-servations regarding PipeDRAM ’s practical deployability. First, 

PipeDRAM ’s area cost and complexity are well within previ-ous area budgets reported by DRAM vendors for commodity DRAM chips [25,72,73,131,353] that include non-conventional on-die logic. For example, ( i) JEDEC standardized per row acti-vation counting (PRAC) in DDR5 [354], which requires DRAM chips to keep an activation counter for every row and to in-crement and compare it against a threshold with in-die logic; MINT [355] reports the area overhead of such per-row counters in an SK hynix design at approximately 9% of a DRAM chip; and ( ii ) SK hynix fabricated multiply-accumulate units directly in a DRAM chip in Newton [131] (productized as GDDR6-AiM [25]), imposing ∼20% area cost to DRAM (within the imposed 25% area cost that SK hynix defined as budget for in-DRAM compute [131]). Second, PipeDRAM ’s DRAM-side modifications also fit within the three-to-four metal layers in commodity DRAM [310, 311]), since the isolation transistors required for fine-grained activation can be rerouted within the already-present metal layers, as Half-DRAM [306] demon-strates using only a wordline shift and a few metal vias [306]. The metal-track budget is strained only when a mat’s datapath is widened [311]; PipeDRAM instead computes at narrow mat granularity, with an HFF-width inter-mat carry path that adds 

no coarse-pitch wiring tracks and inter-subarray transfers that reuse the existing master-data-line routing [310]. Therefore, 

PipeDRAM requires no circuit of unprecedented complexity and is deployable within commodity DRAM’s existing struc-ture and metal budget. It is important to note that, if enabled, fine-grained DRAM [304–312], SALP [316], and LISA [223] would independently provide performance and energy benefits beyond assisting PipeDRAM , as they were originally proposed to improve the efficiency of commodity DRAM chips broadly. Our evaluation does not include these independent benefits of the three schemes; so the cost of these structures that support 

PipeDRAM would actually be amortized further if they are enabled for general deployment. 

## 7. Related Work 

To our knowledge, PipeDRAM is the first processing-using-DRAM (PUD) architecture that executes bit-serial/bit-parallel PUD operations directly over horizontally laid-out data with-out requiring any data transposition overheads. PipeDRAM 

architecture has three major novel aspects: ( i) the bit-positions of each data element within a cache line are interleaved across the DRAM mats of a single DRAM chip, one bit-position per mat, without incurring runtime data transposition overheads; (ii ) the mats of a DRAM chip operate as pipeline stages that process successive bit-positions concurrently under a statically computed iterative modulo schedule; and ( iii ) carry propa-gation between pipeline stages is decoupled from computa-tion through an inter-subarray data copy path. We highlight 

PipeDRAM ’s key contributions by contrasting them with state-of-the-art PIM designs. 

Processing-Using-DRAM. Prior works propose different ways of implementing bit-serial/-parallel PUD operations (e.g., [130, 185, 187, 190, 191, 194, 211, 216, 217, 225, 235, 292]). Such works could benefit from PipeDRAM ’s key mechanisms to enable PUD operations over horizontally laid-out data using their specific PUD primitive. Among bit-serial approaches, MIMDRAM [235] introduces fine-grained mat-level access and inter-/intra-mat data movement to enable MIMD execu-tion of data-independent PUD operations across DRAM mats. 

PipeDRAM builds on MIMDRAM’s fine-grained PUD substrate but repurposes it for a fundamentally different goal, i.e., rather than exploiting data-level parallelism across multiple indepen-dent PUD operations, PipeDRAM exploits bit-level parallelism 

within a single PUD operation by treating each mat as a pipeline stage for one bit-position of a bit-serial/bit-parallel compu-tation. Proteus [292] distributes the bit-positions of a data word across multiple DRAM subarrays within a bank, leverag-ing LISA [223] to propagate intermediate (e.g., carry) values between subarrays and enabling bit-parallel PUD arithmetic. 

PipeDRAM exploits a similar form of bit-level parallelism but at a finer granularity (mats instead of subarrays) and deploys a modulo scheduling-based pipeline execution model that over-laps bit-independent PUD primitives across pipeline stages, sustaining high throughput with simple statically-defined con-trol logic. In contrast, Proteus serializes all primitives within each bit-position and requires simultaneously operating mul-tiple subarrays in a bank (constrained by the DRAM power-delivery limits, e.g., tFAW ), without providing a scheduler that can keep high-throughput PUD execution across bit-positions. 15 Our evaluation shows that PipeDRAM outperforms both MIM-DRAM (by 11.8 ×) and Proteus (by 80.4 ×) in execution time, on average across twelve real-world applications, while con-suming 25.4 × and 38.0 × less energy, respectively. 

NVM-Based PUM Architectures. Several processing-using-NVM works [208, 209, 356–363] exploit the concept of parti-tions (i.e., dividing a memory array into smaller, independently operable sections) to accelerate in-memory computation. FE-LIX [356] segments ReRAM crossbar bitlines with transistor switches to enable multiple stateful logic gates to execute con-currently within the same row. PartitionPIM [357] formalizes this mechanism into serial, parallel, and semi-parallel execu-tion modes, where semi-parallel mode enables inter-partition communication for carry propagation across bit-positions. Ar-itPIM [358] generalizes the partition concept into a technology-agnostic framework, showing that partitions can reduce bit-parallel addition execution time by assigning each partition to a different bit-position of the same operand. These ap-proaches exploit partitions for spatial bit-level parallelism, but do not temporally overlap the execution of successive operations across partitions: once an operation completes, the next begins from scratch with no pipelined steady state. RACER [208, 209] goes further by organizing ReRAM tiles into a pipeline with bit-striped data placement and inter-tile ReRAM buffers that serve as pipeline registers, propagating micro-ops tile-to-tile via hardware queues. This is conceptu-ally closest to PipeDRAM ’s pipelined execution across DRAM mats. However, RACER relies on fixed hardware micro-op queues rather than a software modulo scheduler, limiting its ability to exploit operation-specific parallelism (e.g., overlap-ping bit-independent primitives that do not lie on the carry chain). A key distinction that separates PipeDRAM from the NVM-based PUM architectures is that PipeDRAM targets com-modity DRAM, which serves as the system’s main memory. Because DRAM is shared between the host processor and PUD execution, it must preserve the horizontal data layout that modern processors rely on for cache line abstraction, memory interleaving, and high memory throughput. NVM-based PUM systems often operate as dedicated accelerators with custom data layouts and do not face this constraint. 

Avoiding Dual-Data Layout in PNM Systems. DRAM-based PNM systems (e.g., [18,22,139,364,365]) often suffer from similar dual-data layout issues we identify for PUD systems (§3), where data words need to be localized within a DRAM chip (or DRAM bank) prior to computation using data transfor-mation routines, leading to added performance overheads, pro-gramming, and system complexities [18,22,139,364–366]. Prior works (e.g., [139, 365]) aim to mitigate such a dual-data layout issue in PNM systems either via ( i) DIMM-based data relayout hardware units that filter out continuous cache line blocks of data before DRAM–CPU data transfer [139, 366], or ( ii ) spe-cialized huge-page based data allocation routines that align PNM data within a DRAM bank of a DRAM chip [365]. Even though such solutions are effective at alleviating the dual-data layout issue in PNM systems, they fall short when applied to PUD systems for two main reasons. First, PUD systems impose a more restrictive environment where data must be properly aligned across all levels of the DRAM hierarchy since computa-tion happens in-situ . This requirement means that employing flexible DRAM interleaving and data allocation routines (as in [139, 365, 366]) cannot fully mitigate the dual-data layout issue in PUD systems, since neither the memory controller nor the operating system (OS) has enough information regarding internal DRAM organization (i.e., how the address maps to a DRAM subarray and DRAM mat [367–369]). PipeDRAM ad-dresses this issue by leveraging MIMDRAM’s data allocation routine, which combines huge pages and reverse-engineered DRAM address mapping to align pages further into the DRAM hierarchy (across subarrays and mats) [235,370]. Second, while PNM systems operate under a conventional horizontal data layout (spanning a single DRAM row), PUD systems operate over a vertical data layout (spanning multiple DRAM rows). This means that moving between a PUD-friendly data layout and the CPU-friendly data layout fundamentally requires read-ing multiple DRAM rows to compose a single cache line. A DRAM-side data re-layout accelerator (e.g., [61, 371]) could potentially improve such a process, but it cannot eliminate the data transposition overhead caused by multiple DRAM row activations. PipeDRAM fundamentally eliminates the need for data transposition by employing a PUD-friendly horizontal data layout using its MABM interleaving mechanism (§4.2). 

## 8. Conclusion 

We introduce PipeDRAM , a processing-using-DRAM (PUD) architecture that eliminates the need for runtime data layout transformation, enabling bit-serial/bit-parallel PUD execution 

directly over horizontally laid-out data, which is friendly to and conventional in compute-centric (CPU, GPU, TPU) sys-tems. PipeDRAM combines three new key mechanisms: ( i) a 

mat-aware bit mapping (MABM) mechanism that determin-istically reorganizes bits within each cache line to enable PUD-friendly data placement in a horizontal layout, with-out incurring any additional data movement, latency, or area overheads; ( ii ) a software-assisted pipelined execution model 

that statically schedules PUD primitives across DRAM mats to overlap bit-dependent and bit-independent computation; and ( iii ) a hierarchical in-memory data copy scheme that sepa-rates latency-critical carry propagation from non-critical in-termediate data transfers, ensuring that inter-mat communi-cation does not dominate PUD execution time. Our detailed evaluation demonstrates that PipeDRAM significantly outper-forms three state-of-the-art PUD systems in both performance and energy efficiency, while incurring low area cost on top of a DRAM chip and CPU die. We conclude that PipeDRAM 

effectively bridges the gap between the horizontal data lay-out of modern memory systems and the vertical layout re-quired by PUD architectures, unlocking the full performance and energy efficiency potential of in-DRAM computation. To enable further research, design, and adoption of PUD sys-tems, we freely open-source the PipeDRAM infrastructure at

22 A. Artifact Appendix 

A.1. Abstract 

This artifact contains the analytical PUD, instrumented ap-plication workloads, immutable paper inputs, plotting pro-grams, MABM RTL, and validation tools needed to reproduce 

PipeDRAM ’s evaluation results. It compares SIMDRAM, MIM-DRAM, Proteus , and three PipeDRAM configurations while preserving the submitted timing, energy, batching, and transpo-sition methodology. We provide two workflows. ( i) The quick 

workflow regenerates and validates all figures from frozen pa-per CSVs. ( ii ) The full workflow rebuilds and executes every redistributable paper-scale workload before regenerating the figures. The artifact also supports one-command reproduction of an individual figure and a guided notebook with separate cells for every experiment. 

A.2. Artifact Checklist (Meta-Information) 

• Algorithm: Per-primitive PUD simulation, dependency-graph construc-tion, modulo scheduling, PipeDRAM hierarchical carry transfer, MABM bit permutation. • Program: Python, C/C++, Verilog, and shell scripts. • Compilation: GCC/G++, GNU Make, Yosys, and Icarus Verilog. • Model: Analytical DRAM latency/energy model with fixed submitted pa-rameters; instrumented application-level PUD cost model. • Data sets: Included frozen CSVs; deterministically generated kmeans input; optional checksum-verified heartwall video; frozen x264 results without restricted SPEC source or media. • Run-time environment: Ubuntu 24.04 x86-64, Python 3.12. • Hardware: Quick mode requires a conventional x86-64 system. Full mode is recommended on a 32-thread host with 64 GB RAM. No GPU is required. • Execution: Automated quick, full, area-only, and per-figure workflows. • Metrics: Latency, throughput, energy, normalized performance/W, trans-position overhead, mat utilization, carry overhead, crossover point, and area. • Output: One-page PDF figures, auxiliary PNGs, regenerated CSVs, JSON metrics, and textual validation results. • Experiments: Figures 4 and 9–14, application workload evaluation, dataset verification, and area/RTL evaluation. • Disk space: Approximately 1 GB for setup and quick mode; reserve 10 GB for full mode and generated inputs. • Preparation time: Approximately 5–15 minutes after system packages are available. • Experiment time: Quick mode normally completes in under two minutes. Full mode is hardware-dependent; allow up to 24 hours on an evaluator machine. • Available to evaluators: Tokenized Zenodo preview; permanent record DOI: https://doi.org/10.5281/zenodo.21530459 .• Code licenses: MIT for project-authored code; retained third-party bench-mark notices and licenses. • Data licenses: Frozen numerical results are included. Restricted SPEC source/media and the heartwall video are excluded. • Workflow automation: Shell scripts and a Jupyter notebook. • Archived: DOI: 10.5281/zenodo.21530459. 

A.3. Description 

A.3.1. How to Access. The artifact is archived under https: //doi.org/10.5281/zenodo.21530459 . Extract the ZIP and enter the artifact_ae directory. The directory is indepen-dently distributable and does not read files from its parent directory. The root README.md is the primary entry point. 

PipeDRAM_AE.ipynb provides a guided, figure-by-figure inter-face. 

A.3.2. Hardware Dependencies. Quick reproduction and area verification require no specialized hardware. A few CPU cores, 2 GB RAM, and roughly 1 GB free disk space are suffi-cient. The full workflow uses paper-scale problem dimensions. We recommend 32 hardware threads, 64 GB RAM, swap space, and 10 GB free disk. Large PolyBench allocations rely on the operating system’s virtual-memory support. CPU RAPL and GPU measurements are immutable paper inputs and are not remeasured because they depend on the original evaluation platforms. 

A.3.3. Software Dependencies. The supported environment is Ubuntu 24.04 x86-64. Install:             

> sudo apt update sudo apt install -y build-essential python3-venv \texlive-extra-utils poppler-utils \fonts-liberation yosys iverilog

The artifact pins NumPy, Matplotlib, adjustText, SciPy, Pil-low, and their Python dependencies in requirements.txt .The setup script creates an in-artifact virtual environment and checks GCC, G++, Make, PDF tools, Yosys, Icarus Verilog, and 

vvp .

From artifact_ae :

> ./scripts/setup.sh

A.5. Experiment Workflow   

> ./scripts/reproduce.sh quick ./scripts/validate.sh quick

This regenerates Figures 4 and 9–14 plus the area compar-ison from immutable paper inputs. It then checks numerical claims, PDFs, labels, rasterized renderings, reference check-sums, MABM RTL, and path isolation.   

> ./scripts/reproduce.sh full ./scripts/validate.sh full

When the verified heartwall video is available:     

> ./scripts/reproduce.sh full \--heartwall-input /path/to/test_4k.avi ./scripts/validate.sh full

Full mode rebuilds and runs 2mm, 3mm, covariance, doitgen, fdtd-apml, gemm, gramschmidt, backprop, PCA, and kmeans. It also builds heartwall and runs it when the verified video is supplied. x264 always uses its frozen result. Generated files are placed under generated/ ; immutable references are never overwritten. 

A.5.3. Individual Figures. Each figure supports a lightweight replot and a full experiment path:     

> ./scripts/reproduce_figure.sh 10 replot ./scripts/reproduce_figure.sh 10 full

23 ./scripts/reproduce_figure.sh area full 

Figures 4, 10, and 11 consume application CSVs; their full mode regenerates those results. Figures 9 and 12–14 execute their analytical simulator experiments directly. The notebook caches full workload preparation so multiple data-dependent figure cells do not repeat it. 

> ./scripts/reproduce_area.sh

This verifies that 1.11 + 0 .60 + 0 .15 = 1 .86% , confirms that the 1,350-entry schedule requires 5,400 bytes and fits in 16 KiB, synthesizes MABM to zero logic cells using Yosys, and checks the permutation/inverse round trip using Icarus Verilog.

A.8. Troubleshooting and Notes 

• If setup reports a missing command, install the Ubuntu pack-ages listed under software dependencies. • A heartwall checksum failure means the video differs from the exact paper-scale input. Omit the argument to use the frozen result. • A kmeans checksum failure indicates a missing, corrupt, or non-reference generated input. Remove it and rerun the generation script. • Rendering mismatches usually indicate an unpinned Python environment or missing Liberation Sans fonts. Remove 

> .venv

, rerun setup, and reproduce again. • Full workloads intentionally use paper-scale dimensions and may allocate several gigabytes. Quick mode is the recom-mended path on a constrained system. • The package excludes development logs, caches, build prod-ucts, and large generated inputs. Workflow scripts recreate them as needed.
